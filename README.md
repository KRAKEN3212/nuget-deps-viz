# nuget-deps-viz

Консольная утилита на Python, которая строит граф зависимостей пакета NuGet и рисует его через Graphviz. Сделана как практическая работа по конфигурационному управлению (вариант 19).

Зависимости программа собирает сама: скачивает `.nuspec` нужной версии пакета через NuGet API и разбирает его. Ни `dotnet`, ни `nuget.exe`, ни сторонние библиотеки для этого не используются, только стандартная библиотека Python.

## Что нужно для запуска

- Python 3.9 или новее
- Graphviz, если нужна картинка. Скачать можно с https://graphviz.org/download/. При установке на Windows отметьте пункт про добавление Graphviz в PATH. Без Graphviz программа всё равно работает и сохраняет `.dot` файл, только PNG не будет.
- Интернет для работы с настоящим репозиторием NuGet. Тестовому режиму сеть не нужна.

Устанавливать через pip ничего не надо.

## Запуск

На Windows:

```
run.bat -p <пакет> [опции]
```

На Linux и macOS:

```
./run.sh -p <пакет> [опции]
```

Скрипты просто вызывают `src/main.py`, поэтому можно запускать и напрямую: `python src/main.py -p <пакет> [опции]`.

| Опция | Что делает |
|---|---|
| `-p`, `--package` | имя пакета, обязательная |
| `-r`, `--repo` | адрес репозитория (по умолчанию `https://api.nuget.org/v3/index.json`) или путь к файлу в тестовом режиме |
| `-t`, `--test-mode` | читать граф из файла, а не из NuGet |
| `-v`, `--version` | версия пакета, если не указана, берётся последняя стабильная |
| `-a`, `--ascii-tree` | дополнительно вывести дерево зависимостей текстом |
| `-f`, `--filter` | не учитывать пакеты, в имени которых есть эта подстрока (регистр не важен) |
| `-F`, `--framework` | целевая платформа, например `net8.0`, `netstandard2.0`, `net462` |
| `-l`, `--load-order` | вывести порядок загрузки зависимостей |
| `-o`, `--output` | как назвать `.dot` и `.png` |
| `--no-show` | не открывать картинку после построения |

Примеры:

```
run.bat -p Microsoft.EntityFrameworkCore -v 8.0.0 -F net8.0 -a
run.bat -p Serilog.AspNetCore -v 8.0.0 -F net8.0 -f Microsoft
run.bat -p Microsoft.Extensions.Logging -v 8.0.0 -F net8.0 -l
run.bat -p A -t -r tests/repos/cycle.txt -a
```

Опцию `-F` лучше указывать. В `.nuspec` зависимости разбиты на группы по платформам, и без `-F` программа берёт их все сразу. Для современных пакетов это раздувает граф: у `Microsoft.Extensions.Logging 8.0.0` получается 88 пакетов вместо 6, потому что подтягиваются зависимости для старого .NET Standard 1.x.

## Как это работает

1. Программа запрашивает служебный индекс репозитория (`index.json`) и находит в нём адрес хранилища пакетов (`PackageBaseAddress`).
2. Скачивает список версий пакета и выбирает нужную.
3. Скачивает `.nuspec` этой версии и достаёт из него зависимости. Если задана платформа, берётся подходящая группа, как это делает NuGet: сначала точное совпадение, потом более старая версия той же платформы, потом .NET Standard.
4. Для каждой зависимости из её диапазона версий (`[1.0, 2.0)`, `8.0.0` и т.п.) выбирается наименьшая подходящая версия. NuGet поступает так же.
5. Граф обходится в ширину (BFS) через очередь, без рекурсии. Каждый пакет попадает в очередь один раз, поэтому циклы не вешают программу. Найденные циклы выводятся отдельно и рисуются красным.
6. Если зависимости какого-то пакета получить не удалось (сеть упала, нет подходящей версии), построение останавливается с ошибкой и кодом возврата 1. Неполный граф программа не выдаёт.

## Тестовый режим

Вместо настоящего репозитория можно подать текстовый файл, где пакеты названы большими латинскими буквами:

```
# A зависит от B и C
A: B C
B: D
C: D
D:
```

В папке `tests/repos` есть готовые примеры:

- `simple.txt` простое дерево
- `diamond.txt` ромб, когда один пакет нужен двум другим
- `cycle.txt` цикл A → B → C → A и пакет, зависящий сам от себя
- `big.txt` граф побольше, на нём удобно проверять фильтр
- `broken.txt` файл с ошибкой, чтобы показать сообщение о ней

## Тесты

Тесты написаны на стандартном `unittest` и лежат в папке `tests`. Сеть им не нужна: вместо NuGet подставляется заглушка с заранее заготовленными ответами, а граф берётся из файлов `tests/repos`.

```
run.bat test
./run.sh test
python -m unittest discover -s tests -t .
```

Проверяется разбор параметров и все ошибки в них, сравнение и диапазоны версий, разбор `.nuspec`, выбор платформы, обход графа, фильтр, циклы, порядок загрузки, остановка при сбое на вложенном пакете, DOT и ASCII-дерево.

## ASCII-дерево

С опцией `-a` граф выводится ещё и деревом. Пакет, который уже был раскрыт выше, повторно не раскрывается и помечается `(*)`. Возврат по циклу помечается `(цикл)`.

## Сравнение с настоящим NuGet

Я проверял результат на трёх пакетах под `net8.0`: создал пустой консольный проект, добавил в него пакет через `dotnet add package` и сравнил список из `dotnet list package --include-transitive` и `obj/project.assets.json` с выводом утилиты.

| Пакет | Пакетов у утилиты | Пакетов у dotnet | Расхождения |
|---|---|---|---|
| Microsoft.Extensions.Logging 8.0.0 | 6 | 6 | нет |
| Microsoft.EntityFrameworkCore 8.0.0 | 11 | 11 | нет |
| Serilog.AspNetCore 8.0.0 | 24 | 24 | нет |

Состав пакетов и версии совпали полностью. Отличия есть в другом.

- У NuGet нет понятия «порядок загрузки». `dotnet restore` скачивает пакеты параллельно, а в `project.assets.json` они лежат по алфавиту. Порядок, который выводит утилита, это топологическая сортировка: каждый пакет стоит после всех своих зависимостей. Так их действительно можно подключать по очереди, но сам NuGet такой список не печатает.
- Штатные средства графа не рисуют. `dotnet list package --include-transitive` даёт плоский список без связей, а Visual Studio показывает дерево в обозревателе решений. Связи между пакетами видны только в `project.assets.json`.
- Если не указать `-F`, утилита объединяет зависимости всех платформ. NuGet так никогда не делает, он всегда собирает граф под конкретную платформу проекта. Из-за этого в объединённом режиме граф больше, и в нём может появиться цикл, которого на самом деле нет (например, у `Microsoft.Extensions.Logging` без `-F` находится цикл через `System.Memory` и `NETStandard.Library`).
- При конфликте версий NuGet применяет правило «ближайший побеждает», а если пакет нужен двум веткам с разными минимальными версиями, поднимает версию до большей. Утилита оставляет ту версию, которую встретила первой при обходе в ширину, то есть ближайшую к корню. На проверенных пакетах это дало тот же результат, но на сложных графах версии могут разойтись.
- Подбор платформы упрощён. NuGet учитывает больше случаев совместимости (Xamarin, UWP, профили PCL и т.д.).

## Структура

```
src/
  main.py          точка входа, вывод результатов
  config.py        разбор и проверка аргументов командной строки
  nuget_client.py  работа с NuGet API, версии и диапазоны версий
  frameworks.py    выбор группы зависимостей под платформу
  sources.py       два источника данных: NuGet и тестовый файл
  graph.py         BFS, поиск циклов, порядок загрузки
  visualize.py     DOT, PNG через Graphviz, ASCII-дерево
tests/
  repos/           тестовые репозитории
  test_*.py        тесты
docs/images/       примеры картинок
run.bat, run.sh    скрипты запуска
```

## История

Работа делалась по этапам, каждый этап в отдельном коммите:

1. CLI и параметры с проверкой ошибок
2. получение прямых зависимостей из NuGet
3. транзитивный граф через BFS, фильтр, циклы, тестовый режим
4. порядок загрузки
5. визуализация через Graphviz и ASCII-дерево

После проверки код переложен в `src`, добавлены тесты и скрипты запуска, а функции разбиты на более мелкие, чтобы код проходил требования к стилю.
